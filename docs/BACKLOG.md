使用者實地調查的結論，**優先序以此為準**：

## 1. 專輯聚集（痛點 A）—— 資料在手上，但抽不出來

**狀態**：資料可得性已驗證，抽取演算法未達可用水準。**這是目前最高優先。**

### 現況：完全不支援

`optimizer.py` 只有 `group_by_artist()`，沒有任何專輯維度；`EnrichedPlaylistItem`
**沒有 album 欄位**。使用者現在無法用這個工具解決痛點 A。

### 好消息：專輯名 98% 都在 API 的 tags 裡

YouTube Data API v3 的 `videos.list` 不回傳專輯欄位，但 Topic 頻道（自動產生的
art track）的 `tags` 帶有結構化資訊。以 ytmusicapi 的 album 當真值比對 11 份樣本
共 623 首：**609/623（98%）的專輯名確實出現在 tags 裡**，且沒有任何一首完全沒有 tags。

tags 的結構長這樣：

```
['SawanoHiroyuki[nZk]', 'サワノヒロユキヌジーク', 'mizuki', 'ミズキ', 'iv', 'CRY', 'クライ']
   └─ 藝人 ──────────┘  └─ 假名 ─────────┘  └合作藝人┘        └專輯┘ └曲名┘ └假名┘
```

### 壞消息：兩個 naive 抽取法都不夠

| 方法 | 規則 | 精確率 | 召回率 |
|---|---|---|---|
| 共現頻率 | 同頻道內出現在 2..n-1 首的 tag | **42%** | 63% |
| 位置法 | Topic 頻道中，曲名 tag 的前一個 | **58%** | 覆蓋 576/623 |

兩者都不能出貨。頻率法在 #8 K-pop（無專輯的廠牌頻道）產生 11 個假群組；位置法在
合作藝人多的清單會抓到藝人名。

**「98% 可還原」與「能抽出來」是兩回事** —— 前者是已知答案去比對，後者才是要做的事。

### ytmusicapi 的角色改變：從執行路徑變成標註來源

這是解除卡關的關鍵。ytmusicapi 的寫入端卡在 cookie（見第 3 條），但**讀取端不需要
任何認證**，而它已經提供了 623 筆帶專輯真值的標註資料。也就是說：

- 抽取器可以用純 API 的 tags 實作，**不引入任何執行期依賴**。
- 開發與迴歸驗證用 `tests/dev/ytm_samples/` 的 ytmusicapi album 當真值。
- cookie 卡關**不阻擋**痛點 A。

### 動工前要先確認

專輯聚集的效益**兩極分化**，必須先能算出來再決定要不要做。以「屬於多曲專輯的曲目
佔比」衡量 11 份樣本：

```
#5 主題清單 55%   #7 電影音樂2 46%   #1 Task3 19%   #4 OST 18%
#3 中文歌2  15%   #6 電影音樂1 12%   #0 舊日文 11%  #10 5%  #2 5%
#9 中文歌3   0%   #8 K-pop      0%
```

中位數只有 **12%** —— 一般播放清單是單曲收藏，每首來自不同專輯，聚集後跟沒聚一樣。
痛點 A 只在「刻意收藏整張專輯」的清單上成立（#5、#7）。所以這個功能必須搭配第 4 條
的聚集效益閘門，不能無差別執行。

## 2. 重複歌曲偵測與排除（痛點 B）

**狀態**：未實作。`youtube_api.py` 的 `delete_item()` 已經寫好，但沒有接上任何 CLI 指令。

### 實測普遍性：比使用者的感受稀有

11 份樣本中：

- **同一支影片被加入多次**：只有 1 份有（Task3 的 4 個多餘項目）。
- **同一首歌的不同版本**：共 13 個，集中在 #3 中文歌2（8）與 #5 主題清單（4）。

但 **#5 那 4 筆是誤判** —— `aLIEz` vs `aLIEz (Remastered)`、`sh0ut` vs
`sh0ut (Remastered)`，正規化時把括號內容去掉才被判成重複。那是使用者刻意收的不同版本。

### 因此必須分兩層，預設保守

| 層級 | 判準 | 預設行為 |
|---|---|---|
| **確定重複** | `video_id` 完全相同 | 可直接建議移除，零誤判 |
| **疑似重複** | 同曲名＋同藝人、不同 `video_id` | **只列出，不動**，逐筆讓使用者確認 |

Remaster / Live / Acoustic / MV 版必須留在「疑似」層，永遠不自動移除。

### 成本

偵測是純本地計算、**0 API 配額**。只有實際刪除才花 `playlistItems.delete` 50 units/筆。
即使普遍性低，這個投入產出比仍然很好 —— 而且 YouTube 介面本身確實沒有找重複的功能，
使用者「不容易排除」的抱怨成立。

## 3. ytmusicapi 寫入端 —— 免 OAuth 的重排路徑

**狀態**：讀取端已驗證，寫入端**卡住**（無法取得瀏覽器 cookie）。

### 背景

兩個獨立的問題指向同一個解法：

1. **推廣瓶頸**：非資訊背景的受測者無法自行申請 Google Cloud OAuth 憑證，卡在 Phase 0
   就無法開始測試。
2. **辨識品質**：現行三層 pipeline（標題 regex → 頻道名 → 模糊比對）本質上是在猜，
   真實清單上會把歌名當藝人（「晩餐歌」→ `晩餐歌`）、把整串標題當藝人
   （`egoist『bang!!!』(tvアニメ「ビルディバイド`），跨語言別名也不會合併
   （`kenshi yonezu` / `米津玄師` 各自成組）。

ytmusicapi 的 `browser` 認證只需從瀏覽器 devtools 複製 headers（不需要 Google Cloud
專案、不需要同意畫面、無配額），且 `get_playlist()` 直接回傳結構化的 `artists` /
`album` / `setVideoId`，`edit_playlist(moveItem=...)` 可直接重排。

### 已查證（2026-09-01，`tests/dev/ytm_probe.py`，11 份樣本）

| 結論 | 證據 |
|---|---|
| ✅ `artists` 修掉現行 pipeline 的猜測失敗 | 日文歌單 188 首中 34 筆分歧，幾乎全是 ytmusicapi 正確 |
| ✅ `album` 可直接取代 LLM 手工逆推專輯歸屬 | Task 2 報告手工推出的 iv 8 首 / V 8 首 / 2V-ALK 5 首，API 給的是 8 / 7 / 6 |
| ❌ artist 是「發行掛名」不是「藝人本人」 | 澤野弘之清單被切成 `SawanoHiroyuki[nZk]:mizuki`、`:Tielle`、`:Yosh` 等 19 組；現行 resolver 只切 5 組，反而更好 |
| ❌ 音樂目錄看不到全部項目 | 192→188、83→82，少的是目錄裡沒有對應曲目的一般 YouTube 影片 |

11 份樣本擴充後的補充結論：

- 現行 pipeline **唯一真正崩潰的是廠牌頻道**：#8 K-pop 有 39% 的項目變成 `unknown`
  （頻道是 `SMTOWN` / `HYBE LABELS` 而非藝人），ytmusicapi 全部正確。其餘 10 份的
  unknown 率是 0~5%。
- 先前用的兩個指標都有偏誤，已作廢：`group_count_ratio` 會把「現行 pipeline 失敗
  折疊成一個 unknown 大桶」誤讀成「分群較好」；`agrees` 一致率會把跨語言標籤
  （`richie jen` / `任賢齊`）誤判成分歧。改用 unknown 率與孤兒率。
- **最重要的角色改變見第 1 條**：ytmusicapi 的即時價值不在執行路徑，而在它免認證
  提供了 623 筆專輯真值，讓純 API 的抽取器有得開發與驗證。

### 結論：不是取代品，是訊號層

- 以 API 快照為準（它才有完整的 `playlist_item_id` 與全部項目），用 `videoId`
  把 ytmusicapi 的 `artists` / `album` **併回去當額外訊號**。
- 中間必須加正規化：去掉冒號後綴 → casefold → 走現有 `artist_aliases.json`。
  實測去冒號後綴可讓澤野弘之那份從 19 組收斂到 9 組。
- 目錄裡沒有的項目**退回現行 pipeline**，不可讓它們從目標順序中消失。

### 卡住的地方

寫入端需要 `setVideoId`，而無認證時是 0/188。認證要跑：

```bash
ytmusicapi browser
```

（**不是** `python -m ytmusicapi` —— 該套件沒有 `__main__.py`。）

它會要求在已登入的 music.youtube.com 開 devtools，找一個 POST `/browse` 請求並複製
request headers。目前卡在抓不到 cookie 資訊。

> ⚠️ 產出的 `browser.json` 裡是瀏覽器 session cookie，**等同帳號憑證**，已加入
> `.gitignore`。它的有效期約 2 年（除非登出），比 OAuth 的 token 更敏感。

### 解除阻塞後要先確認兩件事

1. 一般 YouTube 清單（`PL...`，非 YouTube Music 原生清單）認證後拿不拿得到 `setVideoId`。
2. 單筆 `edit_playlist(moveItem=(from, to))` 是否真的改變順序、語意是否為「移到目標之前」。
   拿 83 首那份試一筆即可（可再搬回來）。

### 風險

非官方 API，會隨 YouTube 改版而壞；正式路徑仍應保留 YouTube Data API v3。

## 4. 聚集效益閘門

**狀態**：「無意義搬動」的部分**已於 v3.7.0 修復**；聚集效益閘門本身尚未實作。

### 尚未實作：聚集效益閘門

11 份樣本顯示，很多清單**根本不適合分群**，但工具不會事先告知，使用者付了配額才發現：

| 情境 | 實測 |
|---|---|
| #10 日文歌單「同歌手放一起」 | 40 組裝 44 首，只移動 4 筆／201 units，等於白跑 |
| #8 K-pop「同團體放一起」 | 移動 59 筆／2,951 units，但最大的一組是 `unknown` 39 首 |
| #9 中文歌3 | 87% 的曲目是單首成群 |

AGENT_SOP.md 的 `unresolved_count` 說明裡**已經寫了正確的知識**（「群組數接近影片數
⋯⋯代表這份清單不適合自動分群」），但掛在錯的觸發條件上 —— #10 的 `unresolved_count`
是 **0**，孤兒率卻是 84%，閘門永遠不會開。與下方已修的那個 bug 是同一種形狀。

建議門檻（在 11 份樣本上乾淨分開，無邊界爭議）：

| 指標 | 門檻 | 攔到 | 不誤攔 |
|---|---|---|---|
| `unknown` 佔比 | ≥ 20% | #8（39%） | 其餘 10 份為 0~5% |
| 有效聚集率（非孤兒項目佔比） | < 30% | #9（13%）、#10（16%）、#6（21%） | #2 45%、#0 48%、#3 64%、#1 69% |

攔到時**不是拒絕執行**，而是先告知再確認，並建議改用其他維度。專輯聚集（第 1 條）
共用同一道閘門，門檻套用到「屬於多曲專輯的曲目佔比」。

### 已修（v3.7.0）：群內排序的「無意義搬動」

2026-09-01 的真實測試中，使用者只要求「把同歌手的影片整齊排序」，但工具額外做了群內
觀看數排序 —— 清單開頭 7 首 tuki. **本來就已經連在一起**，卻為了群內排序多花了 5 筆
移動（250 units）。使用者的原話是「無意義搬動」。

根因有兩層，都不在演算法（LIS 移動數確實是最小的）：

1. `docs/agent/AGENT_SOP.md` 路徑 A 的推薦指令範例**直接寫死了**
   `--within-group-sort viewCount:desc`，Agent 照抄就等於自動加上使用者沒要求的排序。
2. `docs/agent/clarify_scenarios.json` 裡**早就有**這題的追問模板（`missing_sort_field`，
   第一個選項就是「維持原順序」），但它只掛在路徑 C，觸發條件是「認知引擎解析不出欄位」。
   Agent 自己把 view_count 補進 intent 字串後，斷層在進引擎前就被填掉，閘門永遠不會開。

已實作的修法：

- SKILL.md 新增第 0 條規則（不可自行補上使用者沒說的排序維度）。
- Phase 0 新增「需求維度盤點」，判斷依據改為**使用者的原話**，三條路徑一律適用。
- SOP 路徑 A 的範例移除寫死的 `--within-group-sort`。
- Phase 3 新增兩桶拆分。以 Task3-1 實測：只做分組 64 筆／3,200 units，
  加上群內排序 91 筆／4,550 units —— 群內排序多花 27 筆、1,350 units（+42%）。

## 5. 測試產物沒有留存，證據會被下一次執行蓋掉

**狀態**：已確認，尚未修。

`data/` 是單一可變槽位。Task 2 在 11:46 覆蓋了 `data/changes.json` 與 `data/current.json`，
導致 Task 1 真正執行的變更檔已不存在，事後無法稽核（留下的 `changes_optimized.json`
是更早的廢棄版本，模擬後與真實結果只對上 37/192）。

同一次測試的報告中，配額數字也對不上：74 筆移動應為 `1 + 74×50 = 3,701`，報告寫 3,752；
節省量應為 `9,600 − 3,700 = 5,900`，報告寫 5,700。

同樣的情形也出現在 Task 3：`UserTest_Task3-1.md` 是抓取後的原始格式，
`scripts/convert_and_verify_task3.py` 把它轉成 `UserTest_Task3-1.json`、
`tests/verify_json_task3.py` 再拿 JSON 回頭比對 `.md`。`.md` 在轉換後被移除，
這兩支腳本因此**無法再重跑**（不是程式壞了，是輸入被消化掉了）。

修法：每次執行落一個帶時間戳的目錄，**原始格式、變更檔、快照與報告放在一起**，
報告的統計數字由變更檔計算而非另行填寫。轉換型腳本的來源檔案應保留而非刪除。
